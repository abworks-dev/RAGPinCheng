# 用户验收交接规范

本规范用于把 Agent 的技术验证结果交接给用户进行手工验收。它不替代自动测试、构建、冒烟、黄金集或安全检查，也不把普通验收扩大为生产操作授权。

## 适用范围

以下任务完成技术验证后必须提供用户验收清单：

- 新增或改变用户可见功能、页面、交互、提示或错误处理；
- 改变上传、下载、播放、检索、问答、登录或管理员流程；
- 修复需要用户在真实浏览器或业务流程中确认的问题；
- 技术检查无法充分覆盖视觉、可用性、内容正确性或跨步骤状态的改动。

纯内部重构、只读调查、文档整理或没有用户可观察变化的任务，可以不提供手工验收，但最终回复必须说明原因。Agent不能用用户验收代替其本应完成的技术验证。

## 状态定义

- `开发中`：仍有已批准范围内的实现或技术验证未完成；
- `代码完成，待用户验收`：实现和 Agent 能执行的技术验证已完成，等待用户按清单确认；
- `用户验收未通过`：用户发现问题，需记录复现条件并修复；
- `用户验收通过`：用户已经明确确认验收结果。

没有收到用户明确确认时，不得自行记录“用户验收通过”。用户验收失败后，只重新测试受影响范围及必要回归项，不得借机扩大功能范围。

## 交付清单要求

涉及用户验收的最终回复必须区分：

1. Agent 已完成的自动或技术验证；
2. 因环境、权限、真实数据或主观体验而未验证的内容；
3. 需要用户执行的手工验收步骤。

用户验收清单至少包含：

- **目标**：本次要确认的用户可观察结果；
- **前置条件**：所需服务、账号角色、浏览器和配置；
- **测试数据**：最小、非敏感、可清理的数据及格式；
- **进入方式**：启动命令或页面入口；
- **操作步骤**：按顺序编号，一步只做一件主要操作；
- **预期结果**：与每个步骤对应，描述可观察结果；
- **异常与边界**：至少覆盖本次风险最高的失败路径；
- **清理与回滚**：如何安全移除测试数据或恢复状态；
- **失败反馈**：用户需要提供的截图、错误文字、浏览器/时间点和复现步骤；
- **验收结论**：提示用户回复“验收通过”或说明失败步骤。

如果测试环境尚未准备好，应给出准备方法并明确哪些步骤暂时不能执行，不得把未执行项目写成已通过。

## 安全边界

- 优先使用最小、虚构、非敏感的测试数据；
- 不要求用户粘贴密钥、密码、Cookie、客户资料或真实对话；
- 不把索引 Reset、文件删除、数据库破坏性迁移、生产部署、真实媒体删除、密钥轮换或 `docker compose down -v` 写成普通验收步骤；
- 确需高风险操作时，先说明环境、目标、备份和恢复方式，并按 `AGENTS.md` 重新评级和取得专项确认；
- 测试产生的文件、数据库记录和索引状态必须说明是否需要清理以及安全清理方式。

## 推荐输出模板

```markdown
## 当前状态

代码完成，待用户验收。

## Agent 已验证

- 验证项、命令或检查及结果。

## 尚未验证

- 未验证项及原因。

## 用户验收

### 目标

- 要确认的用户行为。

### 前置条件

- 服务、账号、浏览器、配置。

### 测试数据

- 文件、输入内容和限制；不得包含敏感资料。

### 操作与预期结果

1. 操作：……
   - 预期：……
2. 操作：……
   - 预期：……

### 异常与边界

1. 操作：……
   - 预期：……

### 清理

- 安全清理测试数据的方法；不需要清理时明确写明。

### 失败时请提供

- 失败步骤编号；
- 页面截图或完整错误文字；
- 浏览器、账号角色和发生时间；
- 能稳定复现的最短步骤。

完成后请回复“验收通过”；如失败，请回复失败步骤和上述信息。
```

## 验收证据

实现和技术验证结束时，在当前任务最终回复与 PR 描述中记录“代码完成，待用户验收”及未验证项。用户后续明确确认时，在同一任务、PR 或 Issue 中保留“用户验收通过”的证据；发现问题时在同一证据链记录“用户验收未通过”、复现条件和后续修复结果。如果任务受 `TODO.md` 跟踪，同步其状态或最近完成摘要；不为验收结论单独创建仓库日志提交或 PR。生产验收以 workflow run 和 artifact 作为不可变审计证据。
