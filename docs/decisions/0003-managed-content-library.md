# 0003 — 数据库分类与受管内容资料库

- 状态：已批准
- 日期：2026-08-11
- 关联功能：`../features/document-indexing.md`、`../features/transcript-pipeline.md`

## 背景

当前普通资料的分类和身份依赖 `docs/` 物理路径，网页上传会直接创建目录并立即索引；人工在服务器移动文件不会同步 `app.sqlite`、`parents.sqlite` 和 Qdrant。视频及转录又分别保存在 `media/`、`docs/教学视频/` 和转录 artifact 中。团队需要保留编号目录整理习惯，同时获得可审核、可发布、可追踪和可回滚的正式资料管理能力。

## 决策

1. 采用“数据库业务事实 + 受管对象存储”为正式来源，人工目录不再决定分类和索引身份。
2. 分类由 `app.sqlite` 的稳定 ID、`category_key`、显示编号、显示名称和父子关系组成；物理文件夹仅通过显式别名导入。
3. 正式文件按 SHA-256 内容寻址保存。物理对象允许复用，业务资料和跨项目关联保持独立。
4. BIM 工程师可以通过网页或 `inbox/server/<batch_id>/` 投递，负责人审核，管理员发布；只有当前正式版本进入检索。
5. 生成一至四级编号目录只读视图供人工浏览，该视图可以重建且不得被索引器当作事实来源。
6. 现有视频转录版本、审核、发布和正式 head 保持权威；统一资料库只增加关联，不替代成熟的视频状态机。
7. 旧目录采用只读清点、复制、校验、映射、人工确认和候选索引切换，观察期内不移动或删除原目录。

## 备选方案

- 继续以物理目录为事实来源：人工习惯简单，但重命名、移动、网页分类和索引状态无法可靠同步。
- 要求全部旧资料重新上传：实现入口统一，但成本高、容易遗漏并丢失历史路径和视频关联。
- 把视频转录重构进统一版本表：表面一致，但会破坏已验证的发布 head 和播放器链路，当前收益不足。

## 影响

- `app.sqlite` 增加内容领域表和添加式迁移；
- 索引输入改为显式内容元数据，不再依赖目录推导分类；
- Parent、Child 和 Qdrant payload 增加稳定资料版本和分类键；
- 管理端增加分类、批次、审核发布和内容权限能力；
- 部署增加固定 `CONTENT_ROOT` 挂载；
- 生产迁移、备份和切换必须另走 R3。

## 回滚或替代

新能力通过功能开关启用。回滚应用时保留添加式 Schema 和受管文件，恢复旧上传与旧索引读取；迁移观察期内旧 `docs/media` 和旧索引保持可用。后续若引入外部对象存储或项目主数据，可通过新 ADR 替代具体存储或关联实现，但必须保留稳定资料 ID、版本和审计语义。
