# 管理后台视觉设计契约

## 目的与适用范围

本契约定义管理后台的新页面、改版和代码审查的视觉与交互基线。后台服务于 BIM 工程师及资料管理员的高频维护工作，应保持安静、紧凑、工作导向，优先保证扫描、比较、筛选、确认和追溯效率；不按营销页面或展示型仪表盘设计。

适用范围为 `frontend/src/pages/admin/` 及其直接使用的管理后台组件。实现前应先核对当前入口 [AdminLayout.tsx](../../frontend/src/pages/admin/AdminLayout.tsx)、设计 token [tokens.css](../../frontend/src/styles/tokens.css) 和 [ui 组件目录](../../frontend/src/components/ui/)。本契约不替代后端权限校验，也不定义 API 或数据 Schema。

本文中的“强制规则”是实现与代码审查的合入门禁；偏离时必须在变更说明中给出可复核理由和等效保障。“建议规则”是默认选择，可因明确的业务场景调整，但不得削弱对应强制规则。

## 设计资产

### 强制规则

- 使用 [tokens.css](../../frontend/src/styles/tokens.css) 的语义颜色、间距、圆角、控件高度、阴影、层级和动效 token；不得为单个页面复制或硬编码另一套视觉系统。
- 优先复用现有 [Button](../../frontend/src/components/ui/button.tsx)、[IconButton](../../frontend/src/components/ui/icon-button.tsx)、[Input](../../frontend/src/components/ui/input.tsx)、[Alert](../../frontend/src/components/ui/alert.tsx)、[LoadingState](../../frontend/src/components/ui/loading-state.tsx)、[EmptyState](../../frontend/src/components/ui/empty-state.tsx)、[ErrorState](../../frontend/src/components/ui/error-state.tsx) 以及 Dialog、Drawer、Sheet、Badge、Card、Skeleton、Toast。需要新组件时，先确认现有组件不能以组合方式满足需求。
- 正式页面中的 `input`、`select`、`checkbox`、`radio` 和文件选择必须使用已有统一样式，或在同一改动中提供基于 token 的可复用统一样式；不得把浏览器默认外观直接交付到正式页面。
- 不以仅在前端隐藏按钮作为权限控制；页面根据已授予权限组织操作，后端仍是最终授权方。

### 建议规则

- 保持 `AdminLayout.tsx` 的桌面侧栏和小屏横向导航模式；新增管理功能以清晰中文标签加入现有导航语义，而非创建并列的二级后台框架。
- 在确有语义区隔或需要承载独立状态时使用 Card；普通页面区块优先使用标题、间距和边界分隔。

## 信息层级与页面结构

### 强制规则

- 每个页面使用一个可见的 `h1` 和关联的 `aria-labelledby`；页面标题采用当前 `text-ui-2xl` 量级，不使用 hero 级、超大或营销式标题。
- 标题区按“业务上下文或栏目 -> 页面标题 -> 必要的当前范围/摘要 -> 页面级命令”排列。页面级命令位于标题区右侧或其下一行，窄屏时换行而非压缩或遮挡。
- 工具栏按筛选、检索、批量/次要操作、主操作分组；筛选有可见标签或可访问名称，清除筛选和刷新等可逆操作使用次要视觉权重。
- 表单按任务顺序分组，字段标签、帮助/校验信息和控件保持邻近；必填、禁用、错误和提交中状态必须可见且可由辅助技术读取。
- 列表和表格将文件名/对象名称、分类、版本、来源、状态和操作置于稳定、可扫描的位置；状态使用中文标签和语义色，不只依赖颜色。
- 破坏性操作使用 `destructive` 语义并在执行前要求与影响相称的确认；确认、退回、发布等业务操作必须具有明确中文动词和对象上下文。
- 不嵌套卡片，不使用悬浮的页面级卡片堆叠，不使用装饰性渐变、渐变球、营销式大留白或仅用于装饰的图形。

### 建议规则

- 表格中将对象主信息放在首列，次级元数据以较小、弱化文字置于同一单元格的次行；将低频信息移入详情、抽屉或菜单。
- 多项操作优先使用清晰的主操作加溢出菜单；不要让操作列成为无法扫描的按钮墙。

## 控件与操作边界

### 强制规则

- 图标按钮仅用于空间固定、含义熟悉且频繁的操作，如刷新、关闭、返回、展开、更多操作。使用 [IconButton](../../frontend/src/components/ui/icon-button.tsx) 或等价实现，并提供 `aria-label` 和悬停 `title`；图标不应是唯一的破坏性或业务关键操作入口。
- 文本按钮用于提交、确认、退回、发布、上传、保存等需要明确业务含义的命令；主操作使用默认主按钮，同级次要操作用 `outline`、`secondary` 或 `ghost`，危险操作用 `destructive`。
- 选择器用于有限且互斥的预定义选项；选项文本使用面向用户的中文显示名。层级分类选择应显示编号与名称，不将内部键作为唯一可见值。
- 文件选择必须显示允许的文件类型、选择结果和失败原因；在视觉上可隐藏原生 file input 时，仍须有可聚焦、可操作且命名明确的触发控件。
- 开关只用于即时生效且二元的设置；复选框用于独立多选或权限集合；单选框用于同一组互斥选项。三者都必须有可点击标签、键盘可达状态和禁用原因（需要时）。
- 核心的查看、确认、退回、发布操作在所有目标 viewport 都必须可见或可通过同一行/卡片内明确的“更多操作”立即发现；不得要求横向滚动后才可找到。

### 建议规则

- 对不可逆、高影响或需要说明的动作，先在 Dialog 或 Drawer 展示对象、影响和确认文案；可撤销的轻量操作可直接执行并给出 Toast 反馈。
- 相邻操作的文字长度变化不应改变按钮高度、表格行高或工具栏整体布局。

## 响应式与数据密度

### 强制规则

- 桌面端（`>= 1024px`）使用 `AdminLayout.tsx` 的侧栏工作区布局；页面内容保持可阅读的最大宽度，工具栏可横向排列但不得挤压关键命令。
- 平板端（`640px` 至 `1023px`）允许标题区和工具栏换为多行；字段网格减少列数，主要操作保留可见文本，导航保持可横向访问。
- 390px 移动端必须在无横向滚动的页面主体中完成查看单项、筛选、确认、退回和发布。标题、筛选、文件选择和主操作纵向排列或自动换行，文本不得被截断到无法辨识。
- 宽表仅在列之间必须同时横向比较、且逐项列表会损失关键关系时保留横向滚动。滚动容器必须包裹表格本身，首列应包含对象身份，关键操作不得位于只能滚动后才能访问的位置。
- 在移动端将宽表转换为列表或分组行，当行项目可独立处理、信息以对象为中心、或操作为主要任务时。每项先显示名称和状态，再显示分类、版本、来源等元数据，并在项内保留关键操作。
- 使用稳定的网格轨道、最小/最大宽度、固定图标按钮尺寸和预留状态空间。长文件名、批量选择结果、加载文本和错误说明不得溢出、遮挡或造成相邻内容跳动；可换行的正文应换行，标识符可在保留完整值的前提下截断并提供查看方式。

### 建议规则

- 对仍需横向查看的宽表，在窄屏显示简短的滚动提示，并让列标题和单元格保持可读的最小宽度。
- 对频繁扫描的台账，优先减少装饰性间距而非减少字体可读性或触控目标。

## 文案、业务字段与状态

### 强制规则

- 文件名、分类、版本、来源、状态和权限使用中文用户文案。文件名可保留原始文件名；版本以 `v1`、`v2` 等简洁格式显示；来源使用业务可理解名称；权限以“整理”“确认”“发布”等动作名称显示。
- `category_key`、内部 ID、`source_origin` 原值、请求 ID、版本 UUID 等技术字段默认不作为主视觉内容。仅在排障、详情、复制、审计或明确的管理需要中显示，并以“分类标识”“内部编号”“来源标识”等中文标签说明含义。
- `source_origin` 有可理解的显示映射时展示映射后的中文值；无法映射时在受控详情中显示原值，不能伪造含义。
- 每个异步区域都要覆盖：loading、empty、error、disabled、busy、success 和 partial failure。`loading` 保留布局或使用 Skeleton/LoadingState；`empty` 说明当前范围并提供下一步；`error` 说明可恢复动作；`disabled` 保留原因；`busy` 防止重复提交并标示进行中；`success` 给出完成反馈；`partial failure` 同时保留成功结果、逐项失败原因和重试入口。
- 状态文本、图标、颜色和辅助说明共同传达含义；不得仅通过红绿或动画表达成功、失败或处理中。

### 建议规则

- 轮询或后台处理保留最近一次可信数据，避免短暂请求失败清空整个列表。
- 对长耗时任务显示阶段名称、可用的下一步和失败后的恢复路径，而不是仅显示加载动画。

## 可访问性与动效

### 强制规则

- 所有功能均可使用键盘完成：逻辑 Tab 顺序、可见 `focus-visible` 焦点、原生语义优先；自定义菜单、Dialog、Drawer、Sheet 按现有组件模式提供焦点管理、Esc 关闭和触发点回焦。
- 图标、输入、选择器、文件控件和状态区域提供准确的名称、角色和状态；动态完成/失败信息通过适当的 `aria-live` 或 `role=alert/status` 宣布，避免重复播报。
- 文本与背景、边框/焦点与相邻背景的对比度应满足 WCAG 2.1 AA；禁用外观仍要可辨认，但不以低对比度替代禁用语义。
- 尊重 `prefers-reduced-motion`；使用 [tokens.css](../../frontend/src/styles/tokens.css) 的动效时长 token，不把旋转、位移或自动滚动作为理解状态的唯一方式。

### 建议规则

- 使用 `aria-current` 标示当前管理导航，用 `aria-pressed` 标示切换状态；可见提示语优先于只对屏幕阅读器存在的说明。

## 视觉验收与代码审查

### 强制规则

- 新页面和重大改版使用合成、脱敏数据进行视觉验收，至少覆盖：正常数据、长中文文件名、长分类名、多条状态、无权限、空列表、加载、错误、禁用/忙碌和部分失败。不得将真实姓名、员工号、客户名、路径、文档内容、Cookie、令牌或截图中的其他敏感数据用于验收资产。
- 截图至少覆盖桌面 `1440x900` 与 `1280x720`、平板 `768x1024` 和移动端 `390x844`，命名为 `<页面或场景>-<状态>-<宽>x<高>.png`，例如 `managed-content-partial-failure-390x844.png`。
- 新页面：完成上述 viewport 截图、键盘焦点与核心操作路径检查，并验证所有状态。
- 重大改版：完成上述检查，并对受影响的现有核心路径进行改版前后或目标场景的截图比较，确认信息和操作没有丢失。
- 纯样式修改：至少检查受影响组件在三个 viewport 的正常、焦点、disabled/忙碌状态；若修改涉及状态色、动效、可见性或布局断点，则按重大改版处理。
- 代码审查必须核对本契约的设计资产复用、信息层级、关键操作可发现性、窄屏行为、状态覆盖、文字溢出、键盘/ARIA、对比度和隐私要求。

### 建议规则

- 视觉 harness 应固定浏览器缩放、主题、语言和合成数据种子，并将截图按场景保存，便于回归比较。
- 在新增交互状态时补充相应的组件或页面测试；本契约不规定具体测试框架或截图工具。

## 实施边界

本文件是实现与审查契约，不追溯性评价当前页面，也不把某个现有实现细节固化为永久组件 API。需要新增控件或视觉 harness 时，应在其对应改动中评估实现、可访问性和验证范围；本契约本身不引入前端源码、依赖、测试或 workflow 变更。
