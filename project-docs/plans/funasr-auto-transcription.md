- 状态：方案方向已批准；Phase 0 R3 第一批（R3-0～R3-5）已批准，待补充维护窗口后执行
- 风险等级：**R2**（跨模块新增能力，涉及依赖、`app.sqlite` Schema、GPU 调度、后台任务、前后端契约、检索验证和生产开关）
- 审阅结论：2026-07-31 已原则同意方向并完成方案修订；仅批准 Phase 0 R3-0～R3-5，且首选模型仅限 `iic/SenseVoiceSmall@v1.0.0`。**未批准 1h/2h/4h、BGE 共存、Phase 1、业务代码、数据库、生产开关或部署修改**。
- 审批边界：Phase 0～Phase 6 必须逐阶段单独审批。前一阶段完成不自动授权下一阶段。
- 2026-07-31 补充：本计划中所有“实际 GPU 实测 / 跑 CUDA / 压测”行为已升格为 **R3**；公司 Windows GPU 主机是开发兼生产环境；沙箱已完成第三轮审查及紧急停止、标注输入限制、真实样本 warm-up 的 R2 收口和本地 CPU 验证；**未**在实际 GPU 主机上跑过任何 Phase 0 步骤；CI/CD 保持路径 A（人工审批），不采用 push 即部署。

## 1. 目标

允许管理员只上传 MP4，由后台生成与现有 `chunk_transcript()` 兼容的结构化转录稿，再复用现有索引、引用和播放链路；原有人工上传 MP4 + Markdown 流程、检索行为和回答引用必须保持不退化。

完成时具备：

- 自动转录与人工转录在管理端共存；
- 转录任务具备状态、按音频时长计算的进度、失败原因、幂等重试和断点恢复；
- 同一媒体允许保留历史转录版本，但只有一个正式发布版本进入索引；
- 支持“自动索引”和“人工确认后索引”两种模式，默认人工确认；
- 自动生成、人工确认、人工修订三个事实可区分；
- 默认关闭；生产开启须经独立灰度审批。

## 2. 当前依据

### 2.1 已实现的媒体后半段流水线

第一阶段已落地（`project-docs/features/transcript-pipeline.md`、`project-docs/decisions/0001-video-transcript-player.md`）：

- `media_assets` 表位于 `app.sqlite`，已包含 `transcript_origin`（`uploaded | generated`）和媒体处理状态；
- 视频落盘到 `media/<media_id>/original.mp4`；
- 转录 Markdown 落盘到 `docs/教学视频/<安全标题>__<media_id前8位>.md`；
- `index_jobs.media_id`、`Parent.media_id`、`Child.media_id`、`SourceDTO.media_id` 已贯通；
- 已有鉴权 HTTP Range 播放、单实例播放器、引用 seek 和来源播放按钮；
- 当前管理端接口要求同时上传 MP4 与人工 Markdown，自动转录尚未实现。

自动转录只替换“转录稿如何产生”，不得另建一套索引、引用或播放协议。

### 2.2 当前 transcript 分块事实

`src/chunk.py:322-411` 当前行为是：

- 严格解析“说话人 N + `HH:MM:SS`/`MM:SS` + 正文”；
- 一条发言 turn 生成一个 Child；transcript Child **不按**全局 `CHILD_SIZE=256` 再切分；
- 连续 turns 按 `PARENT_SIZE=1200` 贪心组合为 Parent；
- 单个超长 turn 可能产生超过 `PARENT_SIZE` 的 Parent。

因此自动转录需要关注 segment/turn 的长度和边界质量，而不是把 `CHILD_SIZE` 当成 transcript 的直接切分参数。

### 2.3 当前 GPU 条件

- 当前只有一台 GPU 主机、一张 RTX 5060 Ti；本方案不假设第二张 GPU。
- 现有 `gpu_service` 在线承载 BGE-M3 Embedding 与 BGE reranker。
- 自动转录会与在线检索争用同一张显卡的显存和执行时间。
- FunASR、模型权重和完整依赖链的许可证、cu128 / sm_120 兼容性、显存与质量数据尚未实测，不在方案中预设结论。

## 3. 已确认的架构决策

### 3.1 单机单卡、进程隔离

当前唯一目标形态为：

```text
Ubuntu 应用节点
  ├─ 上传、任务状态、产物发布、索引入队
  └─ 向 Windows GPU 节点提交分块音频

Windows GPU 节点（同一台机器、同一张 GPU）
  ├─ gpu_service：BGE Embedding / Rerank（在线优先）
  └─ asr_service：FunASR（独立进程或独立容器、后台低优先级）
```

- 删除原方案的“2×2 真扩”模型。
- “独立”只指独立进程或容器，不代表增加 GPU。
- 独立进程与独立容器的最终选择由 Phase 0 兼容性结果决定。
- 未来增加独立 GPU 属于新方案，不在当前实施范围内。

### 3.2 在线 BGE 始终优先

- Embedding / Rerank 是在线延迟敏感请求，优先级始终高于 ASR。
- ASR 必须先把长音频拆成可恢复的有限时长块。
- ASR 只在音频块边界检查是否需要暂停和让出 GPU；不承诺中断正在执行的 CUDA kernel。
- checkpoint 至少记录已完成音频区间及对应的确定性片段产物，恢复时不得重复发布已完成区间。
- 信号量只能限制并发，不能被描述成任意时刻的 GPU 抢占机制。
- 如果 Phase 0 证明单卡无法在不损害 BGE 的前提下稳定运行，自动转录保持关闭，等待未来独立 GPU；不回退 CPU，也不通过卸载在线 BGE 模型换取 ASR 运行。

### 3.3 引擎选择

- FunASR 是首选引擎。
- 只有 FunASR 在许可证、RTX 5060 Ti 兼容性、中文质量、时间戳、显存、速度或长视频稳定性方面未达到硬门槛时，才测试 faster-whisper。
- 引擎和模型的具体版本必须由 Phase 0 实测落定，不在本方案预设。

## 4. Phase 0 技术验证门禁

### 4.1 授权与环境

- Phase 0 仅 R3-0～R3-5 已获执行授权；因维护窗口起止时间尚未补齐，依赖安装、模型下载与 GPU 执行暂不可开始。具体门禁以 `funasr-phase0-execution-plan.md` 为准。
- 使用公开或专门制作的非敏感测试视频，不使用客户视频或真实敏感资料。
- 不连接生产 Qdrant、`app.sqlite`、`parents.sqlite` 或媒体目录。
- 在隔离进程/容器和隔离产物目录中进行；如需验证 BGE 共存，使用明确的测试窗口和测试服务，不干扰线上请求。
- Phase 0 可以安装沙箱依赖、下载候选模型和运行 GPU 测试，但具体环境、下载来源、缓存位置、日志保留策略须写入 Phase 0 的独立执行计划。

### 4.2 许可证门槛

核查范围必须包括：

- 引擎源码和 Python 包；
- 模型权重与模型卡限制；
- ONNX Runtime、CTranslate2、PyAV、FFmpeg 等实际进入运行链路的组件；
- 容器镜像及其中的二进制分发方式；
- 商用、内部部署、署名、修改和再分发要求。

MIT、Apache-2.0、BSD 等宽松许可证可以进入技术评估；LGPL 不直接淘汰，但必须进入人工合规审查。其他许可证由负责人根据实际链接、调用和分发方式决定，技术方案不得代替法律结论。

### 4.3 GPU 与依赖兼容性

验证：

- RTX 5060 Ti、sm_120、cu128 环境能启动并完成真实推理；
- 不出现 `no kernel image`，不静默回退 CPU；
- 引擎、PyTorch、ONNX Runtime、PyAV/FFmpeg 和 native 依赖无阻断冲突；
- ASR 单独运行时的稳态显存、推理峰值和释放行为；
- 测试 BGE + ASR 共存时的稳态显存、峰值、OOM、BGE 延迟和 ASR 让出行为；
- 长音频分块运行时显存不持续无界增长；
- ASR 失败、退出或 OOM 不改变 `gpu_service` 的健康状态。

### 4.4 质量指标

使用人工标注的短样本计算或记录：

- 中文 CER；
- BIM 术语准确率或召回率；
- 规范编号准确率；
- 时间戳偏差；
- segment 重复率、遗漏率和切词错误；
- 热词开启前后的收益与误纠风险；
- 实时系数 RTF、端到端耗时、稳态/峰值显存和任务失败率。

测试场景至少覆盖：

- 清晰单人录屏讲解；
- 多人会议（本期不做说话人分离，只验证文本连续性）；
- 环境噪声；
- 口音或较快语速；
- 背景音乐；
- 长静默；
- BIM 术语和规范编号密集内容。

### 4.5 长视频递进测试

1. 先完成短样本功能、质量与兼容性测试；
2. 通过后测试 1 小时视频；
3. 前两步通过后再测试 2 小时和 4 小时视频。

任一步出现硬门槛失败，应先记录结论并停止扩大测试，不为凑齐时长而继续消耗资源。

### 4.6 FunASR 退出条件

FunASR 出现以下任一不可接受问题时，才进入 faster-whisper 备选测试：

- 许可证或模型权重无法通过人工合规审查；
- 无法在目标 GPU 环境稳定推理；
- 无法满足长视频分块和确定性恢复要求；
- BIM 术语、规范编号或时间戳质量明显不满足使用要求；
- 单卡资源占用无法在 BGE 优先约束下运行。

具体通过阈值由 Phase 0 独立计划在实测前定义，避免看到结果后调整标准。

## 5. 音频提取边界

允许使用 FFmpeg、PyAV 或等价组件完成：

- MP4 音轨解封装；
- 音频解码；
- 重采样为引擎要求的 16 kHz 单声道格式。

本阶段不做视频重新编码、HLS、多码率视频、缩略图或通用视频转码。

以下输入必须可控失败，管理端显示明确原因并允许更换文件：

- MP4 无音轨；
- 音轨损坏或无法解码；
- 不支持的编解码器；
- 音频时长、文件大小或提取后临时空间超过限制。

系统不自动尝试视频转码修复。

## 6. 转录 JSON、时间戳与确定性 formatter

### 6.1 Canonical JSON

`media/<media_id>/transcripts/<job_id>/transcript.json` 至少包含：

- `schema_version`；
- `media_id`、`job_id`；
- `audio_sha256`；
- 引擎、模型、模型版本和 `config_hash`；
- 音频总时长；
- segments 的规范化 `start_ms`、`end_ms`、正文；
- 原始时间戳及单位（引擎提供且需要保留时）；
- 分块编号和块起始 offset；
- 生成时间及必要的可追溯版本信息。

不假设所有引擎都原生输出“毫秒级绝对时间”；适配器负责把不同单位和分块内相对时间统一到绝对 `start_ms` / `end_ms`。

### 6.2 JSON → Markdown

- `HH:MM:SS` 使用 `start_ms` 向下取整，避免播放器跳到语音开始之后；
- 未启用说话人分离时统一输出“说话人 1”；
- 静默段不生成空发言；
- 过短 segment 按停顿、标点和最大长度确定性合并；
- 单个超长 segment 按句子或标点确定性拆分；
- 合并和拆分规则必须有稳定顺序和固定阈值，同一输入、模型和配置产生相同 Markdown；
- 不使用生成式 LLM 做 formatter 或决定分段；
- 不降低全局 `PARENT_SIZE` / `CHILD_SIZE`，不修改现有 `chunk_transcript()` 标记语法。

### 6.3 分块验证重点

Phase 0/1 必须报告：

- segment/turn 字符长度分布；
- 超长单 turn 数量及处理结果；
- 过短 turn 数量及合并结果；
- Parent / Child 数量；
- 相邻分块重复、遗漏和断句情况；
- 时间戳 seek 误差；
- 自动转录噪声对检索命中和 no-answer 的影响。

视频总转录字数本身不会直接占满一次回答上下文；真正影响检索与上下文的是 segment 粒度、命中排序、Parent 长度和一次召回的相关片段。因此不为自动转录单独放大 `MAX_CONTEXT_CHARS`。

## 7. 数据、任务、版本与发布契约

### 7.1 三套状态各负其责

`media_assets.status` 表示媒体对用户的端到端可用状态：

```text
uploaded → transcribing → transcript_ready → awaiting_review
                                      ├─→ indexing → ready
                                      └─→ failed
```

具体迁移必须兼容当前人工转录跳过 ASR、直接进入 `transcript_ready → indexing → ready` 的路径。

`transcription_jobs.status` 表示一次转录尝试：

```text
pending → running → succeeded
                  ├→ failed
                  └→ cancelled
```

`transcription_jobs.stage` 用于展示任务内部阶段：

```text
queued | extracting_audio | transcribing | formatting | awaiting_review | publishing
```

`index_jobs.status` 继续沿用当前 `pending | parsing | chunking | embedding | done | failed`，不混入 ASR 阶段。

### 7.2 任务字段和唯一约束

`transcription_jobs` 至少需要：

- `id`、`media_id`、创建人；
- 引擎、模型、模型版本、`config_hash`；
- `audio_sha256`；
- `status`、`stage`、错误类型和脱敏错误摘要；
- `processed_ms`、`total_ms`；
- checkpoint / 产物相对路径；
- 创建、开始、完成、更新时间。

约束：

- 同一 `media_id` 同一时刻最多一个活跃任务（`pending` 或 `running`）；
- 重复提交不创建并行任务，API 返回现有活跃任务；
- 同一媒体允许保留多个成功历史任务；
- 只有一个成功版本可以被正式发布并进入索引。

### 7.3 幂等与断点恢复

有效幂等身份至少包含：

```text
(media_id, audio_sha256, engine, model_version, config_hash)
```

- 输入音频、引擎、模型和有效配置都未变化时，可从已完成的音频块继续；
- 引擎、模型或影响结果的配置变化时，从头开始；
- checkpoint 只复用校验通过的完整分块；
- partial 文件不能作为正式产物；正式文件通过同文件系统原子替换发布。

### 7.4 正式版本与审核状态

- `media_assets.transcript_origin` 已存在，继续表示 `uploaded | generated`，不重复新增；
- 另设正交的审核状态，候选值为 `unreviewed | reviewed | edited`；
- 自动生成后尚未确认：`generated + unreviewed`；
- 管理员确认但未改正文：`generated + reviewed`；
- 管理员线下修改并重新上传：保留生成来源和版本关系，同时把正式版本标记为 `edited`；
- 人工上传的既有流程必须向前兼容，具体默认审核值在 Phase 2 Schema 方案中确定。

建议由 `media_assets` 保存当前正式转录版本或当前发布 job 的可空指针；具体字段名和迁移方式在 Phase 2 单独审批。

### 7.5 发布事务

正式发布必须保证以下动作不会留下对外可见的半成品：

1. 校验完整 JSON；
2. 确定性生成并校验 Markdown；
3. 原子发布正式 Markdown；
4. 更新媒体的正式版本、来源与审核状态；
5. 创建唯一的 `index_job`；
6. 更新媒体状态。

数据库事务和文件系统原子替换无法组成单一 ACID 事务，因此 Phase 2 必须定义可重放的提交顺序和启动恢复检查，不得只写“原子替换”而忽略数据库/文件跨系统一致性。

### 7.6 产物保留

- 失败任务及其中间音频块、partial 产物保留 30 天；
- 到期由受控清理任务删除，清理前检查任务状态和正式版本引用；
- 成功发布的原始 JSON、正式 Markdown 和必要审计元数据不适用 30 天清理；
- 磁盘空间不足时停止接收新任务，不通过自动删除正式产物腾空间；
- 真实媒体和正式产物的删除仍属于高风险操作，需单独审批。

## 8. 管理端行为

### 8.1 上传与索引模式

- 保留当前 MP4 + Markdown 人工上传模式；
- `transcript` 为空且功能已启用时，创建自动转录任务；
- 支持“自动索引”和“人工确认后索引”两种模式；
- 默认“人工确认后索引”；
- 第一批生产候选范围仅限非敏感内部培训视频。

### 8.2 人工修订

- 第一阶段不开发在线转录编辑器；
- 管理员可以下载生成的 Markdown，线下修订后重新上传；
- 重新上传产生新的正式版本或明确的版本记录，不静默覆盖已索引版本；
- 发布新版本时只对该媒体执行定向重索引。

### 8.3 状态与进度

管理端至少显示：

- 等待处理；
- 提取音频；
- 正在转录；
- 生成 Markdown；
- 等待人工确认；
- 正在索引；
- 已就绪；
- 失败阶段及可理解的失败原因。

主要进度口径为：

```text
processed_ms / total_ms
```

分块数量可以作为调试信息，但不作为主要用户进度。

## 9. GPU 调度与服务契约

`asr_service` 必须具备：

- 独立进程或容器；
- 独立鉴权 token、端口和健康检查；
- 单任务并发上限；
- 音频块级请求或等价的可恢复执行单位；
- 请求超时、大小限制以及 413 / 503 / OOM 错误契约；
- 当前任务、队列长度和暂停原因；
- 不向管理端或日志暴露服务器绝对路径、token 或敏感正文。

调度器必须：

- 在开始下一音频块前检查 BGE 在线压力和停止条件；
- 在线请求需要资源时暂停启动新 ASR 块；
- ASR 块完成后写入 checkpoint 再继续；
- 服务重启后恢复未完成任务，不能把 `running` 永久遗留；
- ASR 异常不关闭、不重启、不改写 `gpu_service` 状态。

## 10. 自动停止条件

出现以下任一条件时停止接收新的 ASR 任务，并暂停启动新的音频块：

- GPU OOM；
- BGE 在线请求延迟超过批准阈值；
- ASR 健康检查失败；
- 磁盘可用空间低于批准阈值；
- 连续任务失败次数超过批准阈值。

停止 ASR 不得影响：

- BGE 在线服务；
- 现有人工转录上传；
- 已经 ready 的媒体播放；
- 普通文档索引和聊天。

具体阈值必须根据 Phase 0 数据在后续阶段审批，不在当前文档中臆测。

## 11. 分阶段实施

每个阶段启动前单独审批；共七个阶段（Phase 0～Phase 6）。

### Phase 0 — 非生产沙箱技术验证

- 输出：FunASR 许可证/兼容性/质量/显存/长视频报告；如触发退出条件，再补 faster-whisper 对照报告；
- 范围：只在批准的隔离环境安装测试依赖、下载候选模型、运行测试和保存报告；
- 风险等级：R1（非生产沙箱），但仍须单独批准；
- 完成标准：硬门槛、样本、指标、1 小时及必要时 2/4 小时结论完整，可明确判定“进入 Phase 1”或“保持关闭”。

### Phase 1 — 音频提取、Canonical JSON 与确定性 formatter

- 范围：音频提取适配器、JSON Schema、时间戳规范化、短 segment 合并、超长 segment 拆分、JSON→Markdown formatter；
- 使用固定测试夹具，不连接生产服务和数据库；
- 验证：Schema、取整、跨块 offset、空音轨、空 segment、UTF-8、过短/超长 segment、重复执行一致性；
- 风险等级：R2，需独立审批。

### Phase 2 — `transcription_jobs`、状态机、版本与恢复

- 范围：Schema 迁移、CRUD、活跃任务唯一约束、幂等、checkpoint、正式版本指针、审核状态、30 天清理和启动恢复；
- 必须提交 `app.sqlite` 备份、兼容迁移与保留新增表/列的回滚方案；
- 风险等级：R2，需独立审批。

### Phase 3 — 独立 `asr_service` 与单卡调度

- 范围：独立进程/容器、鉴权、并发、块级执行、BGE 优先调度、超时、413 / 503 / OOM、health 和停止条件；
- 不把 ASR 模型加载到现有 `gpu_service` 进程；
- 风险等级：R2，需独立审批。

### Phase 4 — 上传 API 与管理端 UI

- 范围：可选 transcript、自动/人工确认模式、任务状态、时长进度、失败原因、重试、下载、线下修订后重新上传和正式发布；
- 验证管理员、普通用户、匿名、CSRF、失败状态和重启恢复；
- 风险等级：R2，需独立审批。

### Phase 5 — 隔离端到端验证

- 使用独立测试 Qdrant collection、独立 SQLite、独立媒体/文档目录；
- 验证 MP4 → 音频 → 转录 → 审核/发布 → 定向索引 → 检索 → 引用 → 跳播；
- 验证人工转录流程、普通文档、旧会话和播放器不退化；
- 不 Reset、写入或事后破坏性清理当前共享活索引；
- 风险等级：R2，需独立审批。

### Phase 6 — 生产灰度决策

- 仅讨论非敏感内部培训视频；
- 确定 `ASR_ENABLED`、允许分类、默认审核模式、容量、阈值、监控、停止和回滚条件；
- 环境变量默认关闭，管理员页面不能绕过部署级开关；
- 生产部署或真实数据操作仍需按具体环境再次确认；
- 风险等级：R2；若包含生产操作或真实数据，按实际影响提升到 R3 并逐项审批。

## 12. 评测隔离与上游关系

- Phase 0～Phase 4 可以独立推进，不要求等待查询拆分 Phase B 或黄金集第二期完成；
- 自动转录不得污染查询拆分 Phase B 使用的索引、样本或结论；
- Phase 5 只使用隔离测试 collection / 数据库 / 目录；
- 原有 79 题基线先保持冻结；自动转录问题以后作为独立子集加入，不与原始基线混算；
- 自动转录子集单独报告 Recall@1、Recall@5、MRR、no-answer、引用正确性和跳播时间戳；
- 自动转录可以与视频播放器交互增强、Office 收口并行，但不得擅自改变既有 `media_id` / `SourceDTO` 契约；
- 如需扩展来源契约或让自动转录参与查询拆分 Phase B，必须另行提交 R2 方案。

## 13. 风险与兼容性

- **单卡资源争用**：即使进程隔离，也无法隔离显存和 GPU 执行时间；Phase 0 不通过则保持关闭。
- **进程不等于硬件隔离**：ASR OOM 或驱动异常仍可能影响同卡服务，必须验证失败边界。
- **长任务与跨节点传输**：需要音频块级重试、校验和 checkpoint，不能依赖单个长 HTTP 请求。
- **Schema 竞态**：重复提交、重试和服务重启可能产生多个成功版本，必须有活跃任务约束和正式发布指针。
- **文件与数据库一致性**：原子改名不能覆盖跨 SQLite/文件系统事务，需要可重放恢复流程。
- **自动转录噪声**：术语、编号、断句和时间戳错误会改变检索与引用，必须使用独立子集评测。
- **热词副作用**：热词可能误纠普通词；需可关闭、版本化并进入 `config_hash`。
- **磁盘增长**：视频、提取音频、checkpoint、历史 JSON 和 Markdown 会增长，需配额、告警和受控清理。
- **许可证**：引擎、权重与二进制组件许可可能不同，必须按实际部署和分发方式审查。
- **敏感数据**：Phase 0 仅限公开或专制非敏感样本；任何真实资料使用需单独确认授权。

## 14. 回滚

- 总开关默认关闭；关闭后 API 不创建新的自动转录任务，当前人工 MP4 + Markdown 流程保持不变。
- Phase 1：停用提取和 formatter 入口，保留代码与测试夹具。
- Phase 2：保留新增表和向前兼容列，不做破坏性降级；停止任务 worker。
- Phase 3：停用 `asr_service` 和其对外端口/token，不动 `gpu_service`。
- Phase 4：隐藏自动转录入口，仍允许人工转录上传、媒体播放和已有任务只读查看。
- Phase 5：隔离测试资源与当前活索引分离，不需要通过 Reset 恢复生产环境。
- Phase 6：关闭 `ASR_ENABLED`，停止接收新任务；已发布媒体和人工流程继续可用。
- 回滚不自动删除媒体、正式 JSON 或正式 Markdown；删除真实数据需单独审批。

## 15. 明确不做

- 当前方案不增加第二张 GPU，不建设多 GPU 或多机调度；
- 不在同一 `gpu_service` 进程加载 ASR 模型；
- 不使用 CPU 作为单卡失败后的自动回退；
- 不为运行 ASR 卸载 BGE 在线模型；
- 不做视频重新编码、HLS、多码率视频或缩略图；
- 不做声纹识别或说话人分离；
- 不做在线转录编辑器、逐字字幕或字幕轨道；
- 不使用 LLM 改写转录正文或决定分段；
- 不做 Kubernetes、分布式队列、NAS 或对象存储迁移；
- 不改变现有 `media_id` / `SourceDTO` / 播放协议；
- 不改变 `chunk_transcript()` 的标记语法，不调整全局 Chunk 或上下文预算；
- 不改写 `prompts/*.md`；
- 不执行全量索引 Reset、不可逆迁移、生产部署或真实客户视频转录。

## 16. Phase 0 后仍需决定

- FunASR 的具体模型、版本和热词能力；
- 独立进程还是独立容器；
- 音频块时长、短 segment 合并和超长 segment 拆分阈值；
- CER、术语、编号、时间戳、RTF、显存和 BGE 延迟的通过阈值；
- BGE 延迟、磁盘空间和连续失败次数的自动停止阈值；
- 热词来源、版本、敏感词管理和审批责任；
- Phase 2 正式版本指针与审核状态的具体 Schema；
- Phase 6 是否开启，以及自动索引仅允许在哪些白名单分类使用。

## 17. 方案完成标准

以下全部满足，才视为本方案的技术实施完成；不等于已生产上线：

- Phase 0～Phase 5 均已分别获批并有可复核结果；
- FunASR 已通过预先定义的硬门槛，或按退出条件完成备选引擎结论；
- 单卡调度证明 BGE 在线优先且无不可接受退化，否则功能保持关闭；
- 自动转录端到端闭环在隔离环境通过；
- 人工转录、普通文档、旧会话、引用和播放不退化；
- 任务幂等、并发拒绝、断点恢复、正式版本唯一、30 天清理和磁盘停止条件通过验证；
- 默认关闭的部署级开关就位；
- `project-docs/features/transcript-pipeline.md` 按实际完成范围同步；
- `TODO.md` 与 `WORKLOG.md` 按项目规则记录真实状态。

Phase 6 是独立的生产灰度决策，不因技术实施完成而自动执行。
